# Claro task discipline

`claro/CLAUDE.md` is the binding source of truth — its **Invariants** section lists the
six ways to break the app, and its **Design decisions** section explains why the code
looks the way it does. This skill is how to *execute* a task at the established bar.

## Where the work happens

Run every npm command from inside `claro/`. The repo root has no `package.json`, so
there is no workspace, and `ExampleRepo/` next door is a separate unrelated app. If a
script fails with `vitest: command not found`, dependencies simply aren't installed —
`npm install` inside `claro/`, don't go debugging the config.

There is no lint config in this project. Formatting is whatever the surrounding file does.

## Evidence over recall — the core rule

Never assert what you can verify. Before diagnosing, recommending, or contradicting the
user, go look: read the actual file, run the actual test, check the actual token in
`src/styles.css`. This codebase is small and entirely local — there is no excuse for a
guess. See the `verify-root-cause` skill for how to run a hypothesis to ground.

When the user challenges a recommendation, re-derive it from the code rather than
defending it. If the evidence says you overstated it, say so plainly and recalibrate.

## The product gate — apply it before writing code

Claro's thesis is **"fewer, more meaningful things"**. Nav is exactly three items —
Today | Week | Quarter — and the answer to most feature requests is to *deepen one of
those three screens*, not add a fourth place to look. Before building:

- A request for a new section or nav item gets a sentence naming which existing screen
  could carry it instead. Build what was asked; just say what you noticed.
- The caps (3 side quests, 3 weekly actions, 3 non-negotiables, 2 priorities) are
  **product features, not validation**. Never raise, remove, or turn one into an error
  without the user explicitly asking for that change.
- Everything listed under *Out of scope for the MVP* in CLAUDE.md (AI, voice, analytics,
  calendar, notifications, social, payments, gamification) stays out unless the user is
  deliberately reopening it.

## When the user is asking, not requesting

If they're describing a problem, asking "why", or thinking out loud — the deliverable is
the **assessment**. Explain what it means and stop; don't apply a fix until asked. When a
genuine product decision surfaces mid-task, ask rather than pick silently.

## Communication style

- **Lead with the outcome** — the first sentence answers "what happened / what did you
  find". Detail after.
- Complete sentences, not fragment/arrow shorthand. Readable beats terse.
- Reference code as clickable `[storage.ts:118](claro/src/lib/storage.ts#L118)` links.
- Report outcomes faithfully: tests failed → say so with the output; step skipped → say
  that; done and verified → state it without hedging.
- Name what was **verified** versus what is **assumed**. "I ran the suite" and "this
  should work" are different claims.

## Authorization gates

Never do these without explicit user go-ahead in this conversation:

- **Editing anything in `../ExampleRepo`.** It is a read-only reference application and
  must stay byte-for-byte untouched — don't edit it, install into it, or run it.
- **Hand-editing `src/routeTree.gen.ts`.** It is generated by the router plugin.
- **Changing `STORAGE_KEY`, calling `clearState()`, or bumping `CLARO_SCHEMA_VERSION`.**
  These are the only actions in this app that can destroy real user data on disk — a key
  rename silently orphans every existing user's store. See the `data-model` skill.
- **Adding or upgrading a dependency.** The dependency set is deliberately pinned
  (`@vitejs/plugin-react` 5 because 6 hard-requires Vite 8; `lucide-react` ^0.575.0
  because 1.x is a breaking major). Propose the exact package and wait.
- **`git push`**, and committing unless asked.

Local edits, running tests, and running the dev server need no permission.

## Ending a task

1. `npm test` green and `npm run typecheck` clean, both from inside `claro/`.
2. Every behaviour you added or changed has a test that would fail without it — see the
   `feature-tdd` skill. A feature without tests is not finished.
3. Sync docs and memory if project state changed — see the `docs-sync` skill.
4. Final message: outcome first, what was verified versus assumed, and anything left for
   the user to do or decide.
